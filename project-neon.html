담당 범위

맡은 업무

개발 PM 업무

프로토타입 개발이 끝난 뒤 합류해 풀 프로덕션과 심사 빌드 준비에 참여했습니다.
기획/아트/기술 작업이 맞물려 있어, 스펙이 바뀌면 일정과 리소스를 함께 확인했습니다.

Asana와 WBS로 개발 일정과 태스크를 확인했습니다.
리소스 현황판과 외주 발주 리스트로 제작 상황을 살폈고, 외부 협력사의 변경 요청은 기록한 뒤 일정을 협의했습니다.

운영한 회의

개발/아트/사업 회의의 결정 사항을 모았습니다.

회의 후 다시 확인하던 일

회의 내용은 공유됐지만, 누가 언제까지 처리할지 한 번에 확인하기 어려웠습니다.
후속 작업을 진행하려면 담당자와 기한을 다시 물어봐야 했습니다.

  1. Meeting논의
  2. Decision결정 사항
  3. 다시 확인담당자와 완료 기한
  4. Execution실행

개발 회의 프로세스 정리

2024.03 / 개발 회의 프로세스 문서

Demo 단계에서는 같은 작업이라도 부서마다 이해하고 있는 정보가 달랐습니다.
진행 여부, 목표와 세부 스펙, 일정과 담당자가 서로 다르게 공유되었고, 업무 흐름은 암묵적으로 진행되어 규범으로 정리되어 있지 않았습니다.
업무 규범의 첫 단계로 회의 프로세스와 회의별 후속 작업을 정리해 공유했습니다.

  • 목표에 대한 이해 불일치
  • 부서 간 개발 소통과 정보 공유 부족
  • 명확한 업무 프로세스와 규범 부재

  1. 01

    아이디어 회의

    아이디어 단계

    회의 목표
    개발 안건 관련 아이디어 취합
    참석 범위
    부서 내부 인원
    산출물
    아이디어 초안, 예상 완료 일정

  2. 02

    개발 공유 회의

    공유와 피드백 단계

    회의 목표
    아이디어 초안을 협업 부서와 공유하고 피드백 취합
    참석 범위
    연관된 모든 협업 부서 (부서당 최소 1명)
    산출물
    회의록, 개발 기획 초안

  3. 03

    개발 회의

    구현과 방법론 논의 단계

    회의 목표
    개발 구현 방법과 우회 방안 논의, 확정
    참석 범위
    개발 태스크에 직접 연관된 협업 부서
    산출물
    회의록, 개발 기획서

  4. 04

    킥오프 회의

    개발 선언과 착수 단계

    회의 목표
    목표, 스펙, 일정, 담당자를 확정하고 개발 착수 선언
    참석 범위
    개발 태스크에 직접 연관된 협업 부서
    산출물
    회의록, 개발 태스크와 일정, 담당자

각 회의의 산출물은 부서장이 검토하고, 통과하지 못하면 같은 회의를 다시 진행합니다.
회의가 끝나면 다음 회의의 아젠다, 일정, 참석자를 안내하고, 킥오프 이후에는 확정된 태스크를 Asana 프로젝트에 반영합니다.

회의 문화 원칙도 함께 정리했습니다.
회의 목적과 목표 시간을 정하고, 주제가 바뀌거나 결론과 의사결정권자 없이 끝나는 회의를 피하도록 공유했습니다.

결정 사항에 담당자와 기한을 함께 기록

회의가 끝난 뒤에도 할 일을 바로 확인할 수 있도록 담당자와 기한을 함께 기록했습니다.

  1. Decision결정 사항 확인
  2. Issue실행할 일로 정리
  3. Owner담당자 지정
  4. Deadline완료 기한 확인

할 일마다 담당자와 완료 기한을 함께 기록했습니다.
회의가 끝난 뒤에는 해당 항목을 보며 진행 상황과 변경 사항을 확인했습니다.

  4. Follow-up

  1. Meeting

  4. Owner
  5. Deadline
  6. Follow-up
